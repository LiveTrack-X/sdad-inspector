대조한 제안이다. 작성자의 경험담, 도구의 문서상 계약, 통제 실험을 구분한다.
자료를 읽었다는 이유로 해당 도구를 설치하거나 상시 규칙을 추가하지 않는다.

## 규칙을 늘리는 것에 대한 반대 근거도 확인

[Evaluating AGENTS.md 개정판](https://arxiv.org/abs/2602.11988v2)은 최초
2026-02-12, 개정 2026-06-23 자료다. 조사한 설정에서는 컨텍스트 파일이
성공률을 일반적으로 높이지 않았고 추론 비용은 평균 20% 이상 증가했다.
특수한 개발 관행을 전달하는 용도는 인정한다. SDAD를 평가한 논문은 아니므로
이 수치를 SDAD의 비용이나 효과로 옮겨 적을 수 없다.

반면 Vercel의 [2026-01-27 Next.js 평가](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)는
프레임워크 문서 색인을 포함한 AGENTS.md의 이점을 보고했다. 특정 Next.js
과제의 자체 평가이며 모든 저장소에 적용되는 결론은 아니다. 두 자료를 함께
보면 문서의 존재보다 내용·과제·모델·읽기 경로가 중요하다는 가설을 세울 수
있다. 이는 이번 조사의 해석이며 일반적인 생산성 향상이 입증된 것은 아니다.

따라서 SDAD에는 기존의 좁은 문서 라우팅을 유지하고, 일반적인 당부를 더
붙이기보다 실제 오해가 발생한 경계에 테스트를 추가하는 편을 우선한다.

## Rule 5에 적용할 수 있는 구체적인 운영 예시

Vercel의 [Teaching agents product design, 2026-06-25](https://vercel.com/blog/teaching-agents-product-design-at-vercel)는
피드백 수집, 근거 검토, 후보 묶음을 분리하고 최종적으로 사람이 지침·린트·
예시·평가·변경 없음 중 하나를 선택하는 사례를 설명한다. 좁은 파일에 반영하고
관련 검사를 거치는 구조다. 공급자 측 운영 사례이며 비교 실험 결과는 아니다.

SDAD의 기존 Rule 5가 이미 후보와 활성 규칙을 구분하므로 중복 절차를 만들
필요는 없다. 향후 개선 후보는 **문제에 맞는 가장 작은 조치를 고르는 것**이다.

| 실제 문제 | 우선 선택할 조치 | 이번 적용 또는 다음 확인 |
| --- | --- | --- |
| 예시 코드가 실제 TODO로 해석됨 | 파서 수정과 회귀 테스트 | 이번 수정 대상. 전역 AI 규칙으로 우회하지 않는다. |
| 검사 미완료를 성공으로 보여 줌 | 공통 판정 함수와 화면·내보내기 회귀 검사 | 이번 수정 대상. 상태 이름 추가 없이 관찰 완전성을 사용한다. |
| 사람이 상태값을 완료·수락으로 오해함 | 상태 근처의 짧은 설명과 원문 근거 | 이번 화면 설명에 반영. 실제 이해도는 참가자 평가가 필요하다. |
| 동일한 사용자 정정이 반복됨 | 정정 원문·수정·검증의 연결을 검토 | 수신이나 반영 보고만으로 해결했다고 판단하지 않는다. 기존 미완료 참가자 평가를 대체하지 않는다. |
| 특정 프로젝트에서만 실패하는 작업 관행 | 해당 프로젝트의 좁은 지침 또는 예시 | 재현 사례 없이 상시 커널에 추가하지 않는다. |

## 후속 실험과 장기 한계

1. 후보를 고정한 뒤 동일한 과제·모델·추론 설정·도구·예산으로 비교한다.
   기능·권한·기록 보존 오류를 먼저 보고, 읽기량·질문·실행 시간은 보조 지표로
   본다. 환경 준비 실패와 실제 행동 실패를 구분한다. 이는 OpenAI의
   [2026-05-29 외부 평가 지침](https://openai.com/index/trustworthy-third-party-evaluations-foundations/)과도
   부합하지만 지침을 따른 사실만으로 효과가 증명되지는 않는다.
2. 이번 회귀 테스트는 재현한 오류를 막는 근거다. AI가 수개월 동안 더 잘
   일한다거나 사용자가 더 빠르게 판단한다는 근거는 아니다. 기존 참가자
   비교의 미측정 부분은 그대로 남긴다.
3. 문서가 커지면 읽기 상한 때문에 일부 작업이 표시되지 않을 수 있다.
   상한 해제 대신 이번에는 불완전한 집계를 명시한다. 전체 탐색·분할 읽기는
   성능·출처·현재성 보존을 함께 설계할 후속 후보로 남긴다.
4. Inspector의 Markdown 해석은 표시용이다. Doctor 엔진의 구조 검사와
   문법을 자동 통합하거나 결과를 덮어쓰지 않는다. 두 결과가 다르면 각
   출처와 범위를 드러내고, 단일한 완료 판정으로 합치지 않는다.
5. 자율 규칙 추가·자동 완료 승격·자동 외부 실행은 도입하지 않는다.
   새로운 상태 구조가 필요하다는 근거도 이번 조사에서는 확보하지 않았다.
