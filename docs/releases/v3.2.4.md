# SDAD Inspector 3.2.4

Inspector 3.2.4 aligns the product and bundled SDAD versions and makes current
work, verification comparisons and resume baselines easier to understand.
Distribution is gated by the same-commit checks described below. Inspector
0.0.5 and its bundled SDAD 3.2.3 artifacts remain unchanged.

## Changes

- Align the Inspector product version and default bundled SDAD Protocol `v3.2.4`.
  The jump from 0.0.5 follows the shared [versioning policy](https://github.com/LiveTrack-X/sdad-inspector/blob/v3.2.4/docs/VERSIONING.md),
  while preserving distinct repository commits, artifact identities and gates.
- Authenticate the released 3.2.4 engine and extend the compatibility fixtures;
  preserve supported 3.2.1, 3.2.2 and 3.2.3 identities for explicit source inspection.
  Native candidate preparation requires matching product and engine versions.
- Separate current, remaining, checked and deferred TODO work so historical or
  paused items do not look like the current task. Incomplete evidence still
  cannot establish an exact zero or a finished project.
- Let users explicitly select two verification records for comparison. Keep
  command outcome, current source identity, retained log identity and capture
  limits separate; readable explanations preserve the raw reason codes.
- Explain the confirmed absence of a resume baseline without confusing it with
  loading or failure. Saving the current successful observation is an explicit
  starting point for future comparisons, not recovery of earlier changes.
- Keep English, Korean, Japanese and Simplified Chinese UI copy aligned.
  Existing app-owned correction history and draft recovery remain available.
- Limit version synchronization to Windows resources and managed README source
  version lines. Published download URLs and historical release notes stay intact.

## Distribution and compatibility

The release distribution consists of Windows x64, macOS arm64 and Linux x64
archives, each with a **single portable executable**, plus `SHA256SUMS` and
`candidate-manifest.json`. These five assets are published only after the
required gates pass. The archive member remains `SDAD-Inspector.exe` on Windows
and `SDAD-Inspector` on macOS/Linux.

Inspector keeps the built-in `official-sdad-3` ProtocolAdapter and
Snapshot schema 2. State schemas 1–2 and Doctor report schemas 1–2 remain supported;
matching product/engine numbers do not create State v3 or relabel older selected
engines. Inspected projects remain read-only; no migration or automatic state
promotion is introduced.

Existing automatic product update behavior, successful-update acknowledgement,
UI scale controls, and Windows icon refresh for the exact executable path remain
available. A verified replacement carries its release's embedded engine; it does
not fetch an engine independently or alter project files. Only a published,
verified release is eligible for the updater. The MIT License and GitHub Sponsors
links remain unchanged.

## Required validation and limits

Publication requires the candidate's own Python/frontend and public contract
checks, compatibility replay, dependency audit, three native builds, direct
smokes and independent downloaded smokes. The tag workflow must promote the
exact same-commit archives and repeat downloaded smokes. Verify the
exact `v3.2.4` tag, its candidate manifest and the associated workflow results
before comparing assets; those records establish the actual hosted outcomes.
The gate definitions in these notes do not themselves establish a passing run.

Product-updater coverage must include the 0.0.5-to-3.2.4 version jump. Local tests
alone do not prove a published end-to-end update. Each repository keeps separate
release evidence; one successful partner does not establish publication of both.

The distribution remains unsigned: no code signing, notarization or installer is
introduced. Windows requires WebView2, macOS targets Apple Silicon, and Linux
requires its graphical and Qt WebEngine dependencies. Recorded environments do
not establish support for every machine. Receipt matches and exit zero do not
prove requirement coverage, owner acceptance or external service availability.
AI-operated walkthroughs remain separate from participant responses and from
long-term productivity evidence.
