# SDAD Inspector 0.0.5

This patch makes current work and verification easier to inspect, preserves
corrections across source changes, and binds published binaries to the exact
tested candidate. Inspected projects remain read-only.

## Changes

- Prioritize current packet, request interpretation and TODO, followed by resume
  changes and verification. Git and handoff history remain in a disclosure with
  explicit incomplete/unavailable counts.
- Page large documents using source-revision checks. A changed document requires
  an explicit restart instead of mixing different versions.
- List registered verification receipts in pages and inspect only a selected
  record. Command outcome, current source identity, retained log identity and
  incomplete capture remain distinct. Records after the first ten are reachable.
- Preserve explicit app-owned resume baselines and correction drafts/history;
  expose bounded export/archive/restore and source-revision comparisons.
- Keep English, Korean, Japanese and Simplified Chinese controls aligned.
- Check the standalone SDAD receipt collector/connection preview against shared
  versioned conformance cases. These tools are optional source-checkout tools.
- Derive package/resource/download versions from one source, then promote only
  the exact main-commit archives that passed build and downloaded smoke gates.
- Pin UTF-8 in both isolated source-engine invocations and the packaged
  interpreter for Windows machines with a non-UTF-8 default locale. Packaged
  smokes use a Unicode project path with spaces.

## Distribution and compatibility

The release contains one Windows x64, macOS arm64 and Linux x64 archive, each
with one **single portable executable**, plus `SHA256SUMS` and
`candidate-manifest.json`. The manifest binds source commit, build run/attempt,
archive names and digests. GitHub artifact attestations cover all five assets.

Inspector continues to bundle the authenticated official SDAD Protocol `v3.2.3`,
built-in `official-sdad-3` ProtocolAdapter and Snapshot schema 2.
The separately released SDAD 3.2.4 collector/preview is compatible with the
receipt reader. SDAD 3.2.4 Doctor wording is not part of the bundled 3.2.3 engine.
Existing supported 3.2.1/3.2.2/3.2.3 engine identities remain unchanged.

The updater selects the exact platform archive and never downloads an engine,
writes project state or automatically accepts work. No automatic migration is
needed. The archive member is `SDAD-Inspector.exe` on Windows and
`SDAD-Inspector` on macOS/Linux; the destination does not need Python.

Existing automatic product update behavior, successful-update acknowledgement,
UI scale controls, and Windows icon refresh for the exact executable path remain
available. The MIT License and GitHub Sponsors support links are unchanged.

## Validation and limits

Publication requires same-commit Python/frontend checks, source/release/public
contracts, dependency audit, three native builds, direct smoke and independent
downloaded archive smoke on the three hosted platforms. Tag promotion reuses
those exact archives and repeats the downloaded smokes before publication.
The workflow run attached to this tag is the authority for hosted outcomes.
Verify the exact `v0.0.5` tag and its candidate manifest before comparing assets.
Both direct and extracted executable smokes exercise receipt pagination,
malformed-record rejection, source/log identity, and project-file preservation
through the actual packaged API, plus bounded native window startup and exit.

**Unsigned portable release:** no code signing, notarization or installer is
provided. Windows requires WebView2; macOS targets Apple Silicon; Linux requires
its graphical and Qt WebEngine dependencies. Hosted checks cover the recorded
runner environments, not every physical computer or operating-system version.

Matching receipt bytes and exit zero do not prove requirement coverage, user
acceptance or current external availability. AI-operated task walkthroughs are
usability observations, not participant responses or long-term productivity
results. Existing user-evaluation work remains separately recorded.
